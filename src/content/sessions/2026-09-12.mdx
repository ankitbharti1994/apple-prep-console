## Why this session counted more than its content

Phase 1 scheduled Saturday build blocks with a stated purpose — *"anything you only read about gets
written."* **None had run.** 29 Aug was a rest day, 5 Sep fell inside the four-day gap, and the one
piece of work that should have come out of it — [the in-flight dedup pattern](/internals#16-asyncsequence-detached-tasks-in-flight-dedup) —
got built on a Wednesday instead.

Then on 8 Sep [the phase revision](/plan) put phase 2's entire DP track on this same slot. That
changed what the slot was: **a plan resting on a commitment with an 0-for-2 record is a hope.**

So tonight was a test of the slot, not of Swift concurrency. It now has a result, and the result is
the thing worth recording — not because an hour at 10pm is impressive, but because
[the alternative was moving the DP track](/open#saturday-is-overcommitted) rather than leaving it
standing as an intention.

## The clean build that meant nothing

The sequence that got to 259 diagnostics went through four dead ends, and the useful moment is the
one in the middle where **everything appeared to be working**.

```swift
final class Probe {
    var count = 0
}

func probeTest() {
    let p = Probe()
    Task {
        p.count += 1        // expect: capture of non-Sendable type
    }
}
```

The package built clean with no warnings. Two things explain that — the module is already
concurrency-safe, or **the checking is not reaching this code** — and they point in opposite
directions. The probe produced no warning, which settled it, and building the SPM package directly
rather than the app produced the 259.

**This is [the technique the board has been waiting on](/open#distinguishing-input) for three weeks**,
and it arrived somewhere it was not being chased. Every previous instance targeted an algorithm or a
language rule. This targeted a build configuration — and it is the more valuable case, because a
wrong answer from an algorithm eventually shows up in an output, whereas **a checker that is silently
switched off is indistinguishable from success forever.** Same shape as
[asserting on `hashValue`](/open#hashable-what-a-hash-test-proves), caught this time before it was
believed rather than after.

## Same error, two fixes — the part that does not read off the message

Five categories came out of the 259, and the pair worth being able to separate out loud is the one
that looks like a single category:

```swift
static var defaultValue: CGFloat = 0     // stored global state — diagnostic fires
static var defaultValue: CGFloat { 0 }   // computed — clean
```

**Protocol requirements written as `static var` are satisfied by a computed property.** The `var` in
the declaration does not mean storage is required — it means the requirement is not `let`, and
misreading it is what produces the error in the first place.

| | Cause | Fix | `Sendable` helps? | `@MainActor` helps? |
|---|---|---|---|---|
| **1** | Type is not Sendable | Declare the conformance | **Yes** | Sometimes |
| **2** | Type *cannot* be Sendable | Isolate or redesign | No | **Yes** |
| **5** | Storage exists unnecessarily | **Remove the storage** | Irrelevant | Irrelevant |

Categories 1 and 5 print **the same diagnostic text**. So the first question is not *"is this
Sendable"* but **"does this actually need to be stored?"** — and the tell, said in exactly these
words during the session, is *"Sendable or `@MainActor` doesn't solve the issue."* When both obvious
tools are irrelevant, it is category 5.

That also produces the one non-mechanical action on the remaining 255: **scan for
`static var x = <constant>`**. A design system accumulates constants written with `=` out of habit
that never needed storage, and if many are that shape the batch clears with no conformance work at
all.
