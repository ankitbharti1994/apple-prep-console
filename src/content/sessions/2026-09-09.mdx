## What the re-pass measured, which is not what it repaired

Both items came back with one prompt each. The repair is the smaller half of that; the useful half
is what it says about the two failures that produced them on Monday.

| Asked | Faded for | What it cost to restore |
|---|---|---|
| `@Sendable` captures — the boxing | 7 days | **One framing question**, then unprompted and complete |
| In-flight dedup — why store the *task* | 5 days | **One re-framing**, from a design question to a timing question |

Neither prompt supplied a fact. The first asked the question a different way; the second changed
what the question was *about* — from "which design is better" to "what is literally in the
dictionary at 10 milliseconds." **That is the whole intervention, and it was enough both times.**

**Decay is not the same as never having learned it**, and this is the first morning with evidence
for that rather than an intuition. The control case is sitting on the same board: the
[424 stale `maxFreq` argument](/open#the-424-stale-maxfreq-safety-argument) has failed three
attempts and is parked, because there has never been a version of it to restore. One prompt does
nothing for a thing that never landed.

The unwelcome corollary, and it is the mistake the [31 Aug close](/open#sendable-stated-backwards)
already made once: **a cheap repair says nothing about the next gap.** Today's close is
deliberately narrower than that one was.

## The correction inside the correction

The dedup answer is the more interesting of the two failures, because nothing in it was forgotten.

> Storing images gives no retry mechanism on failure.

Every word of that is a real fact about this pattern. It is attached to the wrong implementation.
Storing images stores *nothing* on failure, so the dictionary stays empty and the next caller
retries naturally — the poisoning problem belongs to the **task**-storing version, which is
precisely why the `catch` removes the entry.

**So the detail was recalled correctly and the design it belongs to was lost.** That is a third
category alongside "knew it" and "never knew it", and it is not one this board has had before: a
gap loses the fact, and this lost the fact's owner.

The other correction is a word pair that gets conflated constantly and is worth stating flat:

| | What it is about |
|---|---|
| `async` | **Suspension.** This call may pause and resume later. It says nothing about who else is touching the state |
| Synchronised | **Serialised access.** One at a time. This is where safety comes from |

**Async and unsynchronised is still a race.** Same distinction as "isolation is not a lock" from
2 Sep, met from the other side.

## The heap, and why the concept came first

The request was for the concept before the build, and it was the right call: attempting the
structure without knowing what it is for produces a memorised shape rather than a tool. What makes
a heap worth having is what it *refuses* to do.

Maintaining full sortedness costs more than most problems need. A heap maintains just enough order
to answer one question — **what is the smallest right now** — and the price of that is stated in
the same breath: **an arbitrary search is O(n), no better than an unsorted array.** Fast access to
one extreme and nothing else.

That is what makes [question 13](/coding/13) the case in hand rather than an example. It is solved
by sorting all *m* distinct elements at `O(m log m)`, where a size-*k* heap gives `O(m log k)` — and
at *k* = 5 with *m* = 1,000,000, that is the difference the follow-up exists to ask about. The
problem has been standing since 25 Aug for one reason: there was no heap to replace the sort with.

## The fake worth keeping, and it is a rare one

The build went well by every visible measure — read once, written independently, every test green.
Here is the version that also passes:

```swift
struct NotAHeap {
    private var storage: [Int] = []

    mutating func insert(_ value: Int) {
        storage.append(value)          // no siftUp
    }

    mutating func popMin() -> Int? {
        guard let m = storage.min(),
              let i = storage.firstIndex(of: m) else { return nil }
        return storage.remove(at: i)   // O(n), every time
    }
}
```

**Same outputs, every input, every time.** Pop order sorted regardless of insert order; empty;
single element; duplicates; already-sorted; reverse-sorted. Not one assertion in the suite changes.

This is the cleanest instance yet of [the thing being drilled since 25 Aug](/open#distinguishing-input),
and it breaks the technique in a new place. Every previous fake on that list differs from the real
answer on *some* input, and the work is finding it — `("aab","bab")`, `[1,2,1]`, `("ABACADA", 1)`.
**Here no such input exists.** The two implementations are behaviourally identical and differ only
in cost, and no correctness test can see cost.

So the standing question — *would this still pass against a deliberately broken version?* — returns
**yes**, and the suite is inert anyway. The extension the technique needs: **when the fake differs
only in cost, stop testing behaviour and count work.**

| Implementation | Comparisons, n = 100,000 |
|---|---|
| A real heap — roughly *n log n* | **~1.7 million** |
| Append and linear-scan — *n²/2* | **~5 billion** |

A counter in `siftDown` and two minutes settles it, with no threshold to argue about — one of the
two does not finish. **It was not run**, which makes this the second consecutive problem where the
break was argued and no artifact exists. It carries to Thursday
[as its own item](/open#heap-tests-that-a-linear-scan-would-also-pass).
