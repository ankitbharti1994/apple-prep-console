## The fake that was already in the file

The fake was named before the code, for the seventh time in eight problems: **compare node values
rather than node identity.** It is a good one — `1 → 2 → 2 → nil` has two nodes sharing a value in
a list that ends cleanly, and a value check calls it a cycle.

Then the program hung, and the hang was not in the solution.

| # | Where | Cause |
|---|---|---|
| 1 | `debugDescription` | Walks until `current == nil`. A cyclic list has no `nil` — the print never returns, **before `hasCycle` runs at all** |
| 2 | `==` conformance | `lhs.next == rhs.next` recurses forever on a cyclic list |
| 3 | `hasCycle` | Both pointers advanced one step — fast never outpaced slow, so they never met and never hit `nil` |

The second one is the finding. The `Equatable` conformance was written days earlier for a
different purpose, it compares values — **the exact fake named out loud** — and `==` was used
inside the solution. **Naming a fake does not immunise you against writing it**, and helper code
is where nobody is looking. A two-line test on the named input would have caught it the moment
it ran; [it was not written](/open#distinguishing-input).

## Structure present, mechanism absent

*"Earlier too I was at the right path."* The two variables were there. But equal-speed pointers
never meet, and `==` in place of `===` was the named fake sitting in the solution.

| Date | Problem | The shape that was there | The idea that was missing |
|---|---|---|---|
| 16 Sep | [Merge Two Sorted Lists](/coding/24) | Walk both lists, append the smaller | One pointer that never moves — the dummy |
| 18 Sep | [Linked List Cycle](/coding/25) | Two pointers | **Different speeds**, and **identity** |

Two instances in three days. **Recognising a solution's shape and having the solution are
different states**, and the gap between them is where interview time goes.

## The session that was driven by questions

The internals block went furthest where the prepared list stopped. The three questions asked back —
*why ~50ms for a 40ms sleep*, *will the 40ms be split*, *does partial work carry over* — each landed
on the same fact from a different side: [the main thread does not time-slice](/internals#21-frame-budget-hitches-and-instruments).
Commit waits behind your block; a frame is binary; a hitch is one frame lasting two, and the user
sees the jump that follows it rather than a pause.

The closing restatement was exact, in the user's own words: *"user won't see the new update before
the next cycle even though the data is ready and committed."*
