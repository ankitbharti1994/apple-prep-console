## Where the correct answer was, and why that is the finding

The heap solution is the smaller half of this morning. The larger half is a single comparison.

> **A max-heap of size k is the wrong shape** — you want a *min*-heap of size k, so the cheapest
> thing to evict is the one on top. Push, and pop when the size exceeds k.

That was written into [the Q13 open item](/open#top-k-two-wrong-turns) on 9 Sep, in this record, one
day before it was needed. Asked the question out loud on 10 Sep, the first answer was **max-heap,
"because we need the most frequent."**

This is not the decay pattern the [9 Sep re-pass](/sessions/2026-09-09) measured, and it is not the
never-learned-it pattern of [the 424 argument](/open#the-424-stale-maxfreq-safety-argument). Nothing
was forgotten — the heap was built the day before and *"max-heap is two flipped comparisons and
nothing else"* was stated then. **What failed was selecting between two known things while the
problem's own wording pulled the other way.** "The k *most* frequent" points at a max-heap in plain
English, and the plain-English reading won.

| | What it looks like | What it costs to fix |
|---|---|---|
| Decay | Knew it cold, cannot produce it now | One prompt, twice over, on 9 Sep |
| Gap | Never had a version of it | Three attempts, still parked |
| **This** | **Have it in writing, answer the other way under the question's framing** | **One reasoned reversal — but nothing prevents the next one** |

The repair that seems to hold is not "remember min-heap." It is that **the min/max in the name
describes what is cheapest to remove, not what the problem is asking to keep.** Read that way the
two stop being interchangeable, and the naming stops fighting the intent.

## The complexity argument, in one table

| Approach | Heap size | Per op | Total |
|---|---|---|---|
| Max-heap, push all then pop k | *m* | O(log m) | **O(m log m)** — no better than sorting |
| Min-heap capped at k | *k* | O(log k) | **O(m log k)** |

The first row is the whole reason the follow-up gets asked, and it is why answering "max-heap"
is not a small slip: a max-heap ends up holding everything, so it gives back exactly what the sort
gave. The follow-up has not been answered, only re-implemented.

**What this does not claim.** [Question 13](/coding/13) was already optimal — bucket sort, `O(n)`,
reached on 25 Aug, and it stays the better solution. `O(m log k)` is *worse* than `O(n)`. What
closes is narrower and more useful: the solution the interviewer actually names is now one that can
be **written** rather than only cited. Those have been separate claims in this record since 8 Sep,
and collapsing them at the last step would have been the same error that let depth read as breadth.

## The measurement, and an honest stop

The [thing flagged yesterday](/open#heap-tests-that-a-linear-scan-would-also-pass) — that a heap and
an append-and-linear-scan pass identical suites — now has apparatus. The design detail worth keeping
is not the counter but **where it goes**:

```swift
// The original has the comparison inside the while condition, so counting
// there would miss the final failed check that exits the loop.
private mutating func siftUp(_ index: Int) {
    var i = index
    while i > 0 {
        comparisons += 1
        guard storage[i] < storage[parent(of: i)] else { break }
        storage.swapAt(i, parent(of: i))
        i = parent(of: i)
    }
}
```

A counter in the obvious place undercounts, which would have been a quieter version of the same
error this whole item is about. **That is found by writing the counter, not by reasoning about it** —
and it is the most concrete argument yet for why
[the testing item](/open#distinguishing-input) insists on an artifact rather than an argument.

The second thing building it settled: **read the ratios, not the counts.** Three sizes, because a
single number has nothing to be compared against — and yesterday's proposal was one run at 100,000.

**Status: written, not run.** The item stays open. Three consecutive sessions now where the
reasoning is right and no output exists, which is worth stating flatly rather than softening: what
changed today is that the thing not-run is code instead of prose.
